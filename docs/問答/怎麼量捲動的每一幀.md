# 怎麼量照片頁捲動的每一幀？

[← 回目錄](README.md)

## 先決條件

- **用效能量測版**（`./gradlew assembleBenchmark`，`adb install -r` 直接覆蓋，圖庫保留）。開發測試版可除錯，慢到量不出意義
- **裝好後第一次開會大量 JIT**，第二次開起才是平常的樣子：先開一次、`am force-stop` 再開，才開始量
  - 2107113SG（Android 12）上 `cmd package compile -m speed -f` 回報 `Success`，但 `dumpsys package dexopt` 仍是 `speed-profile [first-use]`，看起來沒生效；不能靠它跳過第一次開的 JIT
- 同一版本每次開 app 的結果會飄，**對照至少各量 3～4 輪**

## 一輪的做法

- 每次動手前確認焦點與上鎖狀態（見[怎麼用 adb 驅動手機做驗收？](用adb驅動手機驗收.md)）
- 同時錄 `gfxinfo` 與 `atrace`，期間用 `input swipe` 快速甩動（60ms 一次、間隔約 0.45 秒）：

  ```bash
  adb shell dumpsys gfxinfo com.xenyaa.videoshot reset
  adb shell "atrace -a com.xenyaa.videoshot -b 65536 -t 22 -o /data/local/tmp/vs.trace gfx view input sched freq dalvik disk" &
  adb shell input swipe 540 1950 540 650 60
  ```

  - 往下甩 `540 1950 → 540 650`，往上甩反過來；起點避開底部導覽列
  - `atrace` 用 `-t` 等它自己結束；中途用 `pkill -INT` 打斷會讓 `-o` 的檔案寫不出來
  - 結束後 `adb shell dumpsys gfxinfo com.xenyaa.videoshot` 看超時幀比例、百分位數、「Slow UI thread」「Slow bitmap uploads」
- **Windows 的 Git Bash 會把 `/data/local/tmp/...` 轉成 Windows 路徑**，先 `export MSYS_NO_PATHCONV=1`

## 讀 trace

- 檔案是 ftrace 文字格式，`tracing_mark_write: B|pid|名稱` 與 `E|pid` 成對；app 主執行緒的 tid 等於 pid，名稱可能顯示成 `<...>`，用 `Choreographer#doFrame` 最多的 pid 認
- 每一幀看 `Choreographer#doFrame` 的長度；慢幀底下常見的子區段：
  - `Recomposer:animation` → `AndroidOwner:measureAndLayout`：捲動時新格子的組合與量測
  - `TextStringSimpleNode::measure`、`TextLayout:initLayout`：文字排版
  - `syncAndDrawFrame` 很長、同時 RenderThread 的 `DrawFrames` 也很長：慢在 GPU／RenderThread，不是 UI 執行緒
- 其他執行緒同時段的 `JIT compiling …`、`decodeBitmap`、`… concurrent copying GC` 也要看：JIT 多代表還沒暖機
- 不要拿 `gfxinfo` 的超時比例單獨下結論：畫面在 60Hz／120Hz 之間切換時，超時的門檻跟著變

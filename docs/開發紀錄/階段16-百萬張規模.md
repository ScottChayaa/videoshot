## 16B：畫面改讀統計表（10-07）

**使用者看得到的改變**
1. Lightbox 頂列不再顯示「第 N / 共 M 張」
2. 查詢結果超過 1000 張顯示「1000+ 張」
3. 查詢候選清單依**全部時間**的張數排序，選時間範圍只拿掉範圍內沒有圖的項目

**做法**：首頁月份標籤、月份選單、候選清單、帳號統計、標籤管理改讀統計表。查詢結果依選取項目的總張數選查法：第一頁小於 `FACET_UNION_THRESHOLD`（5,000）用分段合併，否則沿時間軸掃描；結果張數另有 `FACET_COUNT_UNION_THRESHOLD`（15,000）。

**量測**
| 項目 | 前 → 後 |
|---|---|
| 月份選單 | 0.67 → 0.014 |
| 首頁某月標籤 | 0.95 → 0.06～0.08（目標 0.05，**接受**：量測庫每月 2,010 個地點與標籤，真實圖庫只有幾十個） |
| 候選清單（全部時間） | 11.2 → 0.007 |

## 16C：地點管理與合併（10-08）

**使用者看得到的改變**
- 帳號頁選單多一列「地點管理」（定位針圖示，副標「N 個地點」），列出全部地點與張數（含 0 張），可改名、編輯別名、刪除
- 地點與標籤的編輯抽屜都有【合併到…】（挑目標、確認、不可關閉的「合併中…」）
- **合併後舊名與舊別名併進目標的別名**，查詢的詞彙表、Gemini 解析的地點名、描述關鍵字都認得別名；刪除確認框提醒「要統一請改用【合併到…】」
- 行為變更：標籤「改名成既有名稱」現在也把舊名留成目標的別名（仍不覆蓋既有標籤的種類）

**量測**：repo 合併地點（10 萬張，含別名更新）2.83（目標 3，貼近上限，單次樣本）；SQL 直接合併 1.83～1.86；合併大標籤 3.4～3.5；16B 的讀取沒有退步。repo 合併量測只在 `-e benchMerge true` 時執行（會改動量測庫，跑完要重造）。

**驗收**：JVM 1043 個全綠；最終審查修正（標籤查詢也認別名 `TagDao.idsByNames`、別名欄位壞掉不讓查詢出錯）後儀器測試 `OK (256 tests)`。實機（scott 的圖庫先備份、驗完還原）：地點管理清單張數與資料庫一致；把「加勒比海無人島」合併到「加勒比海」後清單少一個、別名出現舊名、首頁小膠囊不重開 app 就更新。

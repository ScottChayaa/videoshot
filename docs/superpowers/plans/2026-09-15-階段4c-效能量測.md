# T4.10 效能閘門實測（2026-09-15）

量的是 R-3 定義的區間：**進入第二步 → 收斂完成**（`Step2Store` 建立起算，`converging` 翻成 false 為止）。
每一輪都先 `pm clear` 清掉草稿，強迫重新下載 sheet —— 不然第二輪以後量到的是磁碟快取。

## 量測條件與它的限制

| 項目 | R-3 要求 | 實際 | 影響 |
|---|---|---|---|
| 機種 | Android **中階**實機 | **Xiaomi 11T Pro（旗艦）** | 數字偏樂觀 |
| 網路 | **4G 節流** | **WiFi** | 數字偏樂觀 |
| 影片長度 | 短／中／長 | 3:33／10:35／26:53 | 符合 |

**兩項偏離都讓結果偏快**，所以下面的數字是**下限**，不是使用者會遇到的典型值。
（2026-09-15 與 scott 確認：不另外找中階機，接受這個 caveat。）

## 結論：維持進場即收斂

三支影片的 p75 都在 **1 秒附近**，遠低於 R-3 的 3 秒門檻 → **維持進場即收斂，不改成按鈕觸發式**。

**總時間與影片長度幾乎無關**（803 → 1046 ms，影片長了 7.5 倍）。合理 —— 縮圖牆的張數與影片長度無關，
永遠是一兩百張（規格第二節第 1 點），所以工作量本來就差不多。

### 區域平均沒有把預算吃掉

這一項原本是這次量測的主要疑慮：2026-09-15 把 dHash 的取樣從「每格一個像素」改成「每格區域平均」之後，
每一格要掃過整格的 320×180 = 5.76 萬個像素，148 格約 850 萬次。R-3 原本「一兩百次 dHash 是毫秒級」
的估計是以**舊的單點取樣**為前提，所以必須重量。

實測**指紋合計 300～500 ms**，換算約 **每格 3 ms**（含 JPEG／WebP 解圖）。
收斂本身則是 50～80 ms —— 純粹的漢明距離掃描確實是毫秒級。
**取樣的修正沒有讓效能閘門失守。**

### 換到中階機 ＋ 4G 會怎樣

計算約佔一半，其餘是下載、解圖與磁碟寫入。粗估上限：計算慢 3 倍、下載慢 4 倍的話，
1046 ms 會變成大約 3.7 秒 —— 落在 R-3 的「3～5 秒」區間，**動作是「維持，但狀態列要明確可見」**。
狀態列現在就會顯示「正在過濾相似畫面…」，且縮圖牆在收斂完成前已經可以捲動與點選，這一條已經滿足。

**要超過 5 秒（退回按鈕觸發式）需要再慢 5 倍以上，依這組數字不太可能。**

真的在中階機上遇到明顯等待時，優化順序應該是：

1. **每張 sheet 共用一個 `IntArray` 緩衝** —— 目前 `grayscale9x8` 每格各配一次 `IntArray(320*180)`（230 KB），
   一張 sheet 9 格就配 9 次。這是最便宜的一刀。
2. 指紋計算改成跟著 sheet 下載並行（目前是下載一批、算一批）。
3. 最後才考慮退回按鈕觸發式 —— 那會改掉手冊 §四第二步的前三條。

## 怎麼重跑

計時用的 `Log` 已經移除（它們在 `Step2Store` 的收斂完成處與 `StoryboardFrameSource` 的指紋處）。
要重量的話把兩處的 `VSPERF` 記錄加回去，再用這支腳本：

```bash
#!/bin/bash
# 用法：./perf.sh <videoId> <次數>。座標是 1080×2400 上量的，換機器要重新對位
export ANDROID_HOME=$HOME/Android/Sdk; export PATH=$PATH:$ANDROID_HOME/platform-tools
for i in $(seq 1 "${2:-5}"); do
  adb shell pm clear com.xenyaa.videoshot >/dev/null
  adb shell monkey -p com.xenyaa.videoshot -c android.intent.category.LAUNCHER 1 >/dev/null 2>&1
  sleep 4
  adb shell input tap 540 455; sleep 1
  adb shell input text "$1"; sleep 1
  adb shell input tap 166 643
  sleep 50
  adb logcat -d -s VSPERF | tail -3
  adb logcat -c
done
```

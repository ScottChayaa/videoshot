# 階段 16C：地點管理與合併 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 帳號頁新增「地點管理」（比照標籤管理：清單＋張數、改名、編輯別名、刪除）；地點與標籤都有看得見的【合併到…】按鈕，合併後舊名字自動變成目標的別名；合併期間顯示「合併中…」；刪除的確認框提醒「要統一請改用合併」。別名在查詢時視同本名（規則式解析與 Gemini 解析出的地點名都認得別名）。

**Architecture:** 資料層在 16A 的 `place` 表（`aliases` JSON 欄位早就在）上加讀寫：`StatsDao.placesWithUsage`（張數讀 `shot_stat_total`）、`PlaceDao` 的改名／搬移／別名比對，`LibraryRepo` 新增 `allPlacesWithUsage`／`renamePlace`／`mergePlace`／`deletePlace`／`mergeTag`。**所有合併都走同一套規則**：來源的圖改指向目標、來源的名字與別名併進目標的別名、刪掉來源，全部在一個寫入交易裡；統計表由 16A 的觸發器自動跟上。標籤原本「改名撞名＝合併」的路徑改成呼叫 `mergeTag`，所以也會保留別名。畫面層在 `AccountViewModel` 加地點的編輯狀態與共用的合併流程（挑目標 → 確認 → 合併中 → 完成），新增 `PlaceManagementScreen`、`PlaceEditSheet`、共用的 `MergePickerSheet`。地點或標籤改動後通知首頁重新載入、查詢頁重查候選。

**Tech Stack:** Kotlin、Jetpack Compose、Room 2.8.5（`BundledSQLiteDriver`，SQLite 3.50，內建 JSON 函式）、Robolectric（`:app:testDebugUnitTest`）、androidx.test 儀器測試（實機 2107113SG）。

**Spec:** [現行規格](../specs/2026-09-10-videoshot-app-design.md) 第四節（`place` 表、統計表）、第八節（地點條件）、第九節（帳號頁、標籤管理的規則）；16A／16B 計畫的設計決議。Task 5 寫回規格與驗收手冊。

## 設計決議（2026-10-06～07 與 scott 確認）

1. **地點比照標籤**：有別名；地點管理頁跟標籤管理頁同一個樣子（清單列：名稱、「N 張」；點進去是編輯抽屜）。
2. **地點和標籤都有【合併到…】按鈕**：在編輯抽屜裡，按下去從清單挑一個目標，確認後合併。「改名成既有名稱＝合併」的舊路徑保留（確認框照舊）。
3. **合併後舊名字保留成目標的別名**（地點與標籤都一樣，包括「改名撞名」那條路）：查詢打舊名字照樣找得到。來源原有的別名也一起併過去；跟目標本名相同或重複的別名去掉。
4. **合併期間顯示「合併中…」**（不可關閉的對話框）。實機 100 萬張：合併 22 萬筆關聯的大標籤 4.4～4.5 秒、合併 10 萬張的地點 2.3～2.4 秒，scott 選擇接受、不做加速（16B 設計決議 5）。
5. **刪除的確認框加提醒**：地點「這 N 張圖會變成沒有地點；要把它併到別的地點，請改用【合併到…】」；標籤「只解除標籤關聯，圖不會被刪；要把它併到別的標籤，請改用【合併到…】」。
6. **沒有圖在用的地點會留在地點表裡**（16A 起取圖第三步的建議已經把它們藏起來），地點管理頁照樣列出，顯示「0 張」，可以在這裡刪掉。
7. 帳號頁選單從 6 列變 7 列：「地點管理」放在「標籤管理」上面，副標「N 個地點」。

## Global Constraints

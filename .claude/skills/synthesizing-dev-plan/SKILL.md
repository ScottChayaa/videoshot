# 綜合 spec 與 mockup 產出開發計畫

## 核心原則

三份輸入描述的是**不同層次、且會互相矛盾的真相**。計畫不是把它們相加，而是先把矛盾攤開讓人裁決。

- `docs/superpowers/specs/` 最新版 —— 後端與企劃的 brainstorming 成果。**資料模型、技術限制、成本、範圍界定以它為準。**
- `mockups/uiux-v2/驗收操作手冊.md` —— UI/UX 的**目標狀態**。畫面行為、欄位可見性、狀態、動作語意以它為準。
- `mockups/uiux-v2/` 的原型程式碼 —— **實際做到的狀態，會落後於手冊**，兩者不一致是常態。

**未經人確認的裁決不得寫進計畫。** 這是本 skill 的全部重點，其餘都是達成它的手段。

## 輸入來源（本專案固定）

| 用途 | 路徑 | 讀什麼 |
|---|---|---|
| 後端／企劃規格 | `docs/superpowers/specs/` **日期最新的那一份** | 全部。特別是資料模型、實作順序、範圍界定、待確認開放項目 |
| 既有實作計畫 | `docs/superpowers/plans/` | 已完成的階段，避免重複排任務 |
| UI 行為目標 | `mockups/uiux-v2/驗收操作手冊.md` | **主要來源**。已是行為層級敘述，比讀 HTML 準確也省事 |
| UI 資料形狀 | `mockups/uiux-v2/mock-data.js` | 欄位名稱與值域。註解裡的「勿臆造」是硬規則 |
| UI 實際狀態 | `mockups/uiux-v2/*.html`, `app.js`, `styles.css` | 查證手冊的條目**有沒有真的實作**，以及手冊講不清楚的互動 |
| 現況 | `README.md`, `src/` | 目前實作到哪、`Repo` 介面長什麼樣 |

`specs/` 有多份不同日期的規格，舊版是歷史。**只用最新的那一份當基準**，引用時寫出檔名與節次。

## 三個階段，中間有一道人工閘門

### 階段一：抽取畫面契約

逐畫面（登入／首頁／Lightbox／取圖三步／查詢／分類／詳情／設定）列出四件事：

1. **顯示欄位 → 資料來源**。每一項都要標註對應到 spec 資料模型的哪個欄位；沒有對應的明寫「新欄位」，不要含糊帶過。
2. **使用者動作 → 寫入或查詢語意**。「套用到 N 張」這種批次動作要寫清楚 partial update 的規則。
3. **狀態**：空、載入中、錯誤、降級。降級路徑（例如 storyboard sprite 簽章過期退回封面圖）是驗收項目，必須列。
4. **量級假設**：一次回傳幾筆、單筆多大。這是後端評估可行性的實際依據。

### 階段二：delta 對照表與開放問題

每一條 delta 標記五種狀態之一，並保留空白欄給後端填：

| 項目 | 來源（畫面／手冊條目） | spec 對應 | 狀態 | 後端評估 |
|---|---|---|---|---|
| … | … | 第 N 節 ／ 無 | 已涵蓋 ｜ 需擴充（小）｜ 需擴充（大）｜ 超出 v1 範圍 ｜ **互斥（需二選一）** | *留白* |

**「互斥」是獨立狀態，不要硬塞進「需擴充」。** 認證就是例子：spec 選 Cloudflare Access（登入頁由 CF 託管、攔在邊緣），手冊描述的是站內 Google 登入頁 —— 選了 Access，手冊第一節十條驗收項大部分不成立。這種項目沒有「擴充一下就都要」的選項，只能二選一，必須讓人選。

**手冊與原型程式碼不一致時，不要自己裁決哪邊算數。** 手冊寫的是目標狀態，原型可能是還沒做、也可能是後來改變了主意 —— 從檔案上分不出來。作法：列進 delta 表，附上**證據行號**（例如手冊要求首頁欄數隨張數變，但 `styles.css:265` 固定三欄），狀態欄寫「互斥」，交給人。

接著整理**開放問題清單**。每題必須能用「是／否 ＋ 一句理由」或選項編號回答；開放式問題（「你們覺得怎麼做比較好？」）不算數，重寫成選項題。

#### 互斥項：先找有沒有「最壞情況等於 spec」的第三個選項

寫互斥項的選項時，除了 A 與 B，多花五分鐘找一個**漸進式 + 逾時退化**的設計。找得到就列成選項 C，找不到就寫「無」。

取圖第二步是現成例子：手冊要「進場就已收斂」，spec 要「按鈕觸發、只比對已勾選」。第三條路是 —— 進場直連 `i.ytimg.com` 立刻畫出 148 格，dHash 在背景 Web Worker 跑，算完才套用收斂，**逾時（例如 5 秒）就退化成 spec 原本的按鈕**。這樣最壞情況等於 spec，而抓下來的 sheet 後面裁圖本來就要用，不算白做。

**這不是替人做決定。** 你仍然把三個選項交出去讓人選 —— 只是別讓人在「照 UI 做但有風險」和「照 spec 做但 UI 要改」之間硬選，如果實際上有第三條路。

選項 C 必須寫出**判定時機與門檻**（在哪個任務、量測什麼、超過多少就走退化路徑），否則它只是願望，不是選項。

### ⛔ 閘門：停在這裡

**階段二產出後停止。開放問題原封不動交給人，計畫不動筆。**

計畫的任務切分直接取決於這些答案 —— 猜錯不是小錯，是整段任務白做。實測中，同樣的認證衝突，無壓力的 agent 留成開放問題，有時間壓力的 agent 直接裁決「Cloudflare Access 勝出」。差別只在壓力，不在資訊。

**以下全部是違規，即使看起來很負責任：**

- 在計畫開頭加一段「我替你決定的事」／「預設選項」／「假設」，然後照樣寫完任務清單
- 替每個決定附上理由與「推翻的代價」，讓人可以逐條否決
- 說「這些決定沒有被偷渡，掃一眼就能否決」
- 挑一個「合理的預設值」先往下走，標註為可調整
- 把開放問題降級成「風險」，然後排進 sprint

**這些都不是閘門的替代品。** 標示決定 ≠ 取得決定。附上推翻代價，代價仍然是人在會議上才發現、而 29 個任務已經建立在那個答案上。

**被明確要求「不要中間產物、不要問題回來問我、你自己決定就好」時，閘門照樣成立。** 這種指示正是閘門要防的情況 —— 對方不知道有哪些問題，才會說不要問。正確回應是：交出階段二，並用一段話說明為什麼還不能直接給任務清單、以及回答那幾題需要多久。

### 階段三：寫可執行開發計畫

拿到答案後才動筆。計畫要有：

- **任務清單**，順序沿用 spec 的實作順序節次，不要另立一套。
- **每個任務的驗收條件**，盡量直接引用 `驗收操作手冊.md` 的條目原文 —— 驗收標準已經寫好了，重寫只會產生第二套不一致的標準。手冊條目在原型裡尚未實作的，註明「這是新功能，不是照抄原型」。
- **依賴關係**：哪些任務可平行、哪些卡在別人前面。
- **風險**：標記為「需擴充（大）」的項目要單獨列出，附上退路與**判定時機**（在哪個任務的第幾天量測、超過什麼門檻就退回 spec 原設計）。
- **明確不做**：從 delta 表裡狀態為「超出 v1 範圍」的項目複製過來。

輸出到 `docs/superpowers/plans/YYYY-MM-DD-<主題>.md`，日期用今天。

## 詞彙對齊

spec 用 `shot`，mockup 用 `clip`，是同一個東西。**計畫裡統一用 spec 的詞**，並在文件開頭放一行對照說明。其他新舊詞彙落差比照辦理，列進 delta 表。

## 已知一定會出現的 delta（起點，不是全集）

寫階段二時，這幾條至少要處理到：

- **認證方案互斥** —— spec 的 Cloudflare Access vs 手冊的站內 Google 登入頁。二選一。
- **取圖第二步的收斂** —— 手冊要求「一進場就已收斂」，spec 明文「只比對已勾選的，不比對全部」。而且要算 dHash 就得讀像素，與 spec「影像處理一律在瀏覽器」＋零成本前提互相拉扯。**這是全案最大的可行性問號，不要輕輕帶過。**
- **首頁欄數隨當月張數變**（1／2–4／5+）—— 需要每月總數，但既有分頁設計拿不到，可能要新端點。
- **設定值無處可存** —— 「過濾相似強度」「AI 前後秒數」在 spec 資料模型裡找不到對應的表。
- **「套用到 N 張」的 partial batch update** —— 只更新動過的欄位、其他維持各張原值、分兩輪套用互不影響。
- **草稿中途離開** —— 保留／捨棄二選一，草稿存在哪、存多久。
- **文字查詢在 mockup 完全不存在** —— spec 列進 v1，但沒有畫面原型。不要替它臆造畫面。
- **`mock-data.js` 的 `note` / `status` / `tags.kind`** —— 逐一對回 spec 資料模型。`status` 目前只有 `reviewed` 一個值，未整理流程尚未設計。
- **設定頁要求的兩個後端面，spec 十四階段完全沒有** —— 標籤管理（改名／別名／刪除，會牽動既有 shot 的關聯）與縮圖修復（重抓失效的 storyboard）。這兩條容易被漏掉，因為它們藏在設定頁的細項頁裡，不在主流程上。
- **手冊與原型不一致處** —— 至少首頁欄數、月份標籤 `nowrap`、卡片描述、帳號頁漸層 header 這幾條。逐條附證據行號。

## 紅旗 —— 出現就停

- 想直接跳到階段三寫計畫 → delta 沒算，計畫是空中樓閣
- 開放問題自己填了一個答案 → 回到閘門，不管標示得多清楚
- 出現「我替你決定的事」這類段落 → 那就是閘門被繞過的樣子
- 對方說「不要問我、你決定」就照做 → 那正是閘門存在的時機
- 手冊與原型不一致時自己選了一邊 → 附證據行號，交給人
- 寫出 mockup 裡沒有的流程（未整理清單、批次匯入、分享頁…）→ 臆造，刪掉
- 用 `specs/` 裡的舊版規格當基準 → 用最新那份重來
- 自己重寫一套驗收標準 → 引用驗收手冊原文
- delta 表的「後端評估」欄自己填了 → 那一欄是留給人的

## 常見錯誤

| 錯誤 | 為什麼壞 | 改成 |
|---|---|---|
| 產出視覺規格（間距、token、component props） | 那是給前端的 design handoff，後端不看 | 只寫資料契約與行為語意 |
| 逐行讀 HTML 推敲互動 | 慢且容易誤讀 | 先讀驗收操作手冊，程式碼用來查證有沒有實作 |
| delta 只寫「不一致」 | 後端無法據此估工 | 一定要標五種狀態之一 |
| 把互斥選擇標成「需擴充（大）」 | 讀的人會以為加預算就能兩個都要 | 標「互斥」，寫清楚選了 A 會讓哪些驗收項失效 |
| 把 spec 內容大段複製進計畫 | 產生第二份會過期的規格 | 引用節次，不要複製 |
| 風險只寫「有風險」 | 沒有判定時機就等於沒有退路 | 寫明在哪個任務量測、什麼門檻退回 |
